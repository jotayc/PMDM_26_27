Peticiones REST

Una lista de pokémon que la aplicación pide a un servidor de internet. Con esta rama verás qué es una petición HTTP y una API REST, cómo se lee una respuesta en JSON y cómo se hace todo eso en Android sin bloquear la pantalla.

2

Pedir datos a un servidor

2.1Cliente, servidor y HTTP

Hasta ahora, los datos de tus aplicaciones estaban en el propio móvil: en el código, en las preferencias o en la base de datos SQLite. Muchas aplicaciones necesitan datos que están en otro ordenador, conectado a internet, y que cambian sin que tú publiques una versión nueva: el tiempo, los mensajes, el catálogo de una tienda.

Cliente y servidor

El servidor es el ordenador que tiene los datos y espera a que se los pidan. El cliente es el programa que los pide: aquí, tu aplicación. Para hablar entre ellos usan HTTP, el mismo protocolo (el conjunto de reglas para comunicarse) que usa el navegador para traer páginas web. Con HTTP todo va por parejas: el cliente manda una petición y el servidor contesta con una respuesta.

El navegador recibe páginas web para enseñarlas. Tu aplicación no quiere una página: quiere datos sueltos (nombres, números) para colocarlos en sus propias vistas. Por eso no se los pide a una web, sino a una API.

API REST

Una API es la lista de cosas que un servidor te deja pedir y la forma de pedirlas, igual que la carta de un restaurante: solo puedes pedir lo que viene en ella, y de la forma que dice. Una API REST es una API que funciona sobre HTTP con dos ideas: cada cosa que se puede pedir (un recurso: la lista de pokémon, un pokémon concreto) tiene su propia dirección, y el tipo de petición dice qué quieres hacer con ella. La respuesta trae los datos como texto, casi siempre en un formato llamado JSON, que verás en el apartado 3.

Cada API publica su documentación: qué direcciones tiene, qué hay que mandar y qué devuelve. La de PokeAPI está en https://pokeapi.co/docs/v2. Antes de programar nada, se lee.

2.2La dirección: URL base, endpoint y parámetros

Cada petición va a una URL, la dirección completa de lo que se pide, como las que escribes en el navegador. En una API se lee en tres trozos:

TrozoQué esEn la rama
URL baseEl principio común a todas las peticiones a esa API.https://pokeapi.co/api/v2, en la constante URL_BASE.
EndpointEl final de la ruta: dice qué recurso pides. Cada uno está en la documentación./pokemon: la lista de pokémon.
ParámetrosDatos extra para afinar la petición. Van detrás de ?, como nombre=valor, y se unen con &.?limit=100: solo los 100 primeros.

La rama usa un endpoint, /pokemon, pero PokeAPI tiene muchos más: /pokemon/pikachu devuelve los datos de un pokémon concreto, por su nombre, y /type, los tipos. La URL base es siempre la misma.

La URL base es el principio común; el endpoint, la ruta que va detrás y dice qué se pide; los parámetros, lo que hay después de ?, separados por &.

2.3Métodos, cabeceras y códigos de respuesta

Además de la URL, cada petición lleva un método, que dice qué quieres hacer con el recurso. Los dos que vas a ver en la rama son estos:

MétodoPara quéDónde van los datos que mandas
GETConsultar: traer información sin cambiar nada.En la URL, como parámetros.
POSTEnviar información nueva al servidor: un mensaje, un registro.En el cuerpo de la petición, un texto que va aparte de la URL.
Hay más métodos

Las API REST usan también PUT para modificar un recurso que ya existe y DELETE para borrarlo. PokeAPI solo deja consultar, así que solo admite GET.

Cabeceras

Una petición y una respuesta llevan, además, cabeceras: datos sobre el mensaje, como pares Nombre: valor. Accept dice en qué formato quieres la respuesta y Content-Type, en qué formato va el cuerpo de un mensaje. La rama manda Accept: application/json: «contéstame en JSON».

La respuesta empieza siempre con un código de estado, un número de tres cifras que dice cómo ha ido. Lo primero que hace la rama es mirarlo:

CódigoSignificaEjemplo con PokeAPI
200 OKTodo ha ido bien: el cuerpo trae lo que pediste./pokemon?limit=3
400 Bad RequestEl servidor no entiende la petición.Un endpoint que no existe: /pokemn
403 ForbiddenLo has pedido bien, pero no te dejan hacerlo.Cualquier POST
404 Not FoundLo que pides no existe./pokemon/pikachuu
500 Internal Server ErrorHa fallado el servidor, no tu petición.—

Los que empiezan por 2 son de éxito; por 4, un fallo de la petición, y por 5, un fallo del servidor. Pruébalos:

La respuesta: JSON

3.1Objetos y arrays

JSON

JSON es un formato de texto para guardar datos. Solo tiene dos formas de agrupar: el objeto, entre llaves { }, con pares "clave": valor separados por comas, y el array, entre corchetes [ ], con una lista de valores separados por comas. Un valor puede ser un texto entre comillas, un número, true, false, null (sin valor), otro objeto u otro array.

Así es la respuesta de /pokemon?limit=3, ordenada en varias líneas (el servidor la manda en una sola):

count es el total de pokémon que hay; next y previous, las URL para pedir los siguientes y los anteriores, y results, los que has pedido. La aplicación solo necesita el name de cada elemento de results.

Ábrela en el navegador

Escribe https://pokeapi.co/api/v2/pokemon?limit=3 en el navegador: verás exactamente el texto que recibe la aplicación. Antes de programar la lectura de una respuesta, mírala así.

3.2Leer JSON en Java

Android trae las clases JSONObject y JSONArray (paquete org.json), una para cada forma. Se va bajando desde fuera hacia dentro:

LlamadaQué devuelve
new JSONObject(texto)El objeto que hay escrito en el texto.
objeto.getJSONArray("clave")El array guardado en esa clave.
objeto.getJSONObject("clave")El objeto guardado en esa clave.
objeto.getString("clave"), getInt("clave")El texto o el número guardado en esa clave.
array.length()Cuántos elementos tiene el array.
array.getJSONObject(i)El elemento i del array, que es un objeto. Se empieza a contar en 0.

    La petición en Android

    4.1El permiso

    Una aplicación Android no puede usar internet si no lo declara en su manifiesto:

    AndroidManifest.xml · TODO 1
    <uses-permission android:name="android.permission.INTERNET" />

    Es un permiso normal: se concede al instalar la aplicación, sin preguntar al usuario, pero tiene que estar escrito. Sin él, Android no deja abrir la conexión y lanza esta excepción (en el Logcat del emulador):

    Logcat
    java.lang.SecurityException: Permission denied (missing INTERNET permission?)

    4.2Fuera del hilo principal

    Esperar a un servidor puede tardar desde unas décimas hasta muchos segundos, según la conexión. Es justo el caso de las ramas 3.3 y 3.4: una tarea lenta no puede ir en el hilo principal. Aquí, además, Android lo vigila: si una aplicación intenta conectarse a la red desde el hilo principal, lanza NetworkOnMainThreadException sin llegar a enviar la petición.

    La rama hace la petición con una AsyncTask, como en la 3.4. Esta vez la tarea recibe datos y devuelve un resultado:

    MainActivity.java · TODO 8
    private class ConnectionTask extends AsyncTask<String, Void, String> {
    TipoEn la rama
    Params: StringEl método y el endpoint: execute("GET", "/pokemon?limit=100").
    Progress: VoidNo informa de cómo va.
    Result: StringEl texto de la respuesta, que recibe onPostExecute().

    4.3La petición con HttpURLConnection

    Android trae una clase para hacer peticiones HTTP sin librerías: HttpURLConnection (paquete java.net, el mismo de Java de escritorio). Una petición GET son siempre los mismos pasos:

    PasoCódigo
    1. Formar la URL y abrir la conexiónurl.openConnection()
    2. Poner las cabecerassetRequestProperty("Accept", "application/json")
    3. Mirar el código de estadogetResponseCode(), comparado con HTTP_OK (200)
    4. Leer el cuerpogetInputStream(), línea a línea con un BufferedReader
    5. Cerrar la conexióndisconnect(), en el finally

    En la rama todo eso está en getRequest(), que devuelve el texto de la respuesta o null si algo ha ido mal: un código distinto de 200 o una excepción. Las excepciones las recoge su catch, que escribe la traza en el Logcat (líneas System.err). Por eso, con el código de la rama, ningún fallo de conexión cierra la aplicación: la lista se queda vacía y sale un aviso.

      TODO 2-5La clase de las peticiones

      HttpConnectPokemon, en el paquete io (de input/output, entrada y salida), reúne todo lo que habla con el servidor. Sus dos métodos son static: se llaman sin crear ningún objeto, HttpConnectPokemon.getRequest(…).

      io/HttpConnectPokemon.java · TODO 3-4
      private static final String URL_BASE = "https://pokeapi.co/api/v2";

public static String getRequest(String endpoint) {
    HttpURLConnection connection = null;
    String content = null;
    try {
        URL url = new URL(URL_BASE + endpoint);
        connection = (HttpURLConnection) url.openConnection();
        connection.setRequestProperty("Accept", "application/json");

        if (connection.getResponseCode() == HttpURLConnection.HTTP_OK) {
            StringBuilder response = new StringBuilder();
            BufferedReader reader = new BufferedReader(
                    new InputStreamReader(connection.getInputStream()));
            String line;
            while ((line = reader.readLine()) != null) {
                response.append(line);
            }
            content = response.toString();
            reader.close();
        }
    } catch (Exception e) {
        e.printStackTrace();
    } finally {
        if (connection != null) connection.disconnect();
    }
    return content;
}

      Son los cinco pasos del apartado 4.3. El cuerpo llega por partes, así que se lee línea a línea y se va juntando en un StringBuilder, que sirve para construir un texto añadiendo trozos. El finally se ejecuta tanto si todo va bien como si salta una excepción, así que la conexión se cierra siempre.

      El TODO 5 es postRequest(), la petición POST: cambia el método con setRequestMethod("POST"), añade la cabecera Content-Type, avisa de que lleva cuerpo con setDoOutput(true), escribe el cuerpo y devuelve el código de estado. En la rama no se llama, porque PokeAPI no admite POST (contesta 403).

      Cómo se hace hoy

      El código de la rama funciona, pero hoy no se escribiría así. Hay tres cosas que han cambiado.

      6.1En lugar de AsyncTask, ExecutorService y Handler

      AsyncTask está obsoleta desde la API 30, por los motivos que viste en la 3.4. La misma petición, con un ExecutorService para el hilo secundario y un Handler para volver al principal, queda así (compilado y probado en el emulador):

      MainActivity.java · cómo se haría hoy (no está en la rama)
      private final ExecutorService ejecutor = Executors.newSingleThreadExecutor();
private final Handler manejador = new Handler(Looper.getMainLooper());

private void cargarPokemon() {
    ejecutor.execute(new Runnable() {
        @Override
        public void run() {
            final String response = HttpConnectPokemon.getRequest("/pokemon?limit=100");
            manejador.post(new Runnable() {
                @Override
                public void run() {
                    mostrar(response);   // lo que hace onPostExecute() en la rama
                }
            });
        }
    });
}

      getRequest() no cambia: lo que cambia es quién la llama y cómo vuelve el resultado al hilo principal.

      6.2Librerías para las peticiones

      La documentación de Android recuerda que la plataforma ya trae HttpURLConnection, pero que la mayoría de aplicaciones usan una librería que ahorra el trabajo repetitivo: formar la URL, leer el cuerpo y convertir el JSON en objetos de Java. Las dos que cita son estas:

      LibreríaQué es
      RetrofitUn cliente HTTP para Java y Kotlin, construido sobre otra librería, OkHttp. Cada endpoint se declara como un método de una interfaz, y la respuesta llega convertida en objetos.
      KtorUn cliente HTTP de JetBrains pensado para Kotlin. Usa corrutinas, la forma que tiene Kotlin de escribir tareas asíncronas.
      Hoy en día

      Para código nuevo en Java: Retrofit para las peticiones y ExecutorService o las llamadas asíncronas de la propia librería para el hilo. HttpURLConnection sigue siendo válida y es la que conviene entender primero, porque las librerías hacen por debajo esos mismos pasos: abrir la conexión, mandar las cabeceras, mirar el código, leer el cuerpo y cerrar.

      6.3Al girar el móvil

      La petición se lanza en onCreate(). Al girar el móvil, Android destruye la actividad y crea otra, que vuelve a ejecutar onCreate(): la lista nueva empieza vacía y se pide todo otra vez al servidor. En el emulador se ve en el Logcat: sale otra línea DATOS por cada giro. Para guardar los datos entre giros, Android recomienda un ViewModel, un objeto que sobrevive a esos cambios.

      Comprueba · Elige

      Con el código de la rama, la lista ya está cargada y giras el móvil. ¿Qué pasa?

      La actividad nueva ejecuta otra vez onCreate(), que crea una lista vacía y lanza otra petición. En cuanto llega la respuesta, la lista se rellena de nuevo.
