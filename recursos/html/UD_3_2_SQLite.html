Rama UD_3_2_SQLite

SQLite

Una pequeña aplicación que guarda ciudades en una base de datos dentro del móvil. Con esta rama verás cuándo hace falta una base de datos, cómo se crea y se actualiza sin perder datos, cómo se insertan filas y cómo se recorren las de una consulta.

2

El problema: muchos datos con la misma forma

2.1Cuando las preferencias no bastan

En la rama 3.1 guardaste un email en las preferencias. Ahora quieres guardar una lista de ciudades, cada una con su población y su superficie. Con preferencias tendrías que inventar una clave para cada dato de cada ciudad, y llevar la cuenta de cuántas hay:

Y eso es lo fácil. Ordenar las ciudades por población, buscar las que tienen más de cien mil habitantes o borrar la segunda obligaría a leer todas las claves y reescribirlas a mano. Para muchos datos con la misma forma se usa una base de datos.

2.2Tablas, filas y columnas

Una base de datos relacional guarda los datos en tablas, como las que diseñaste en Bases de datos. Recuerda las tres palabras que vas a leer en toda la rama:

TablaUn conjunto de datos con la misma forma: aquí, las ciudades.
ColumnaCada dato que se guarda de todas ellas, con su tipo: el nombre, la población, la superficie.
FilaCada elemento concreto, con un valor para cada columna: Granada, 232000, 88.02.

2.3SQLite

SQLite

Una base de datos relacional que viene incluida en Android. No hay servidor: toda la base de datos es un fichero dentro de la aplicación, que solo ella puede leer. Se maneja con SQL, como cualquier otra.

Hoy en día

La documentación de Android recomienda usar Room, una biblioteca que funciona sobre SQLite, porque las clases de esta rama son de bajo nivel: el SQL no se comprueba al compilar y hay que escribir mucho código repetitivo. Aquí se usan directamente para entender qué ocurre por debajo. También recomienda abrir la base de datos fuera del hilo principal; este ejemplo no lo hace, para no complicarlo.

3

Las clases de la rama

Para trabajar con SQLite, Android da tres clases. La rama añade una propia, DBAccess, que reúne todo lo que toca la base de datos:

ClasePara qué
SQLiteOpenHelperCrea la base de datos y la actualiza. De ella hereda DBAccess.
SQLiteDatabaseLa conexión abierta: con ella se insertan y se consultan datos.
CursorEl resultado de una consulta, que se recorre fila a fila.
Una comparación

DBAccess es como el encargado de un archivo. La actividad no entra al archivo: le pide al encargado «guarda esta ciudad» o «dame la primera». Él abre los cajones (SQLiteDatabase) y le devuelve una bandeja con lo que ha encontrado (el Cursor).

Así, MainActivity solo llama a métodos como insert() o getFirstCity() y nunca escribe SQL. Si mañana cambias la tabla, solo cambias DBAccess.

4

Crear y actualizar: las versiones

4.1onCreate(): la primera vez

La base de datos no existe hasta que la aplicación la pide por primera vez. En ese momento Android llama a onCreate() de tu SQLiteOpenHelper, y ahí se crean las tablas con CREATE TABLE. Después ya existe, y onCreate() no se vuelve a ejecutar nunca.

4.2El problema: tu código cambia, el fichero del móvil no

Imagina que publicas la aplicación con una tabla que solo guarda el nombre de la ciudad. Ana la instala y guarda Granada y Jaén. Un mes después añades la población a tu CREATE TABLE y publicas la versión nueva. Ana la actualiza desde la tienda. ¿Qué tabla tiene ahora en su móvil?

Al actualizar, el móvil de Ana recibe el código nuevo, pero el fichero db_dam es suyo y se queda como estaba. Su onCreate() no se vuelve a ejecutar, porque el fichero ya existe, así que nadie crea la columna nueva. Prueba las dos soluciones que se te ocurrirían primero:

El móvil de Anapublicas una versión con una columna nueva

Ana tiene la primera versión de la aplicación y ha guardado dos ciudades. Publicas la versión nueva, cuyo CREATE TABLE ya incluye poblation. Elige qué haces con la base de datos de Ana al actualizar y mira qué pasa cuando después guarda Málaga.

La aplicación de Ana

Su fichero db_dam

    Ninguna de las dos sirve: con la primera la aplicación deja de funcionar y con la segunda se pierden los datos. Hace falta saber qué versión de la tabla tiene cada móvil y hacer solo los cambios que le faltan, sin tocar sus filas. Y no todos los móviles están igual: unos tienen la primera versión, otros la segunda y otros instalan hoy por primera vez.

    4.3La solución de Android: el número de versión

    Como reformar una casa habitada

    No puedes tirar la casa y construir otra, porque dentro están los muebles de quien vive en ella. Lo que se hace es llevar en la puerta una placa con el número de la última reforma hecha. Cuando hay reformas nuevas, se mira la placa y se hacen solo las que faltan, en orden: a quien tiene la casa de hace dos reformas, se le hacen las dos; a quien solo le falta la última, solo esa.

    Android hace lo mismo. Dentro del propio fichero de la base de datos guarda un número de versión: es la placa. En tu código, la versión que necesitas va en la constante DB_VERSION, que le pasas a SQLiteOpenHelper. Cada vez que cambias las tablas, subes ese número.

    Cada vez que la aplicación abre la base de datos, SQLiteOpenHelper compara los dos números y decide qué método llamar:

    Lo que encuentraLo que hace
    No hay ficheroLlama a onCreate(), que crea las tablas.
    Su versión es menor que DB_VERSIONLlama a onUpgrade(), que hace los cambios que faltan.
    Su versión es igual que DB_VERSIONNada: la base de datos está al día.
    Su versión es mayor que DB_VERSIONLlama a onDowngrade(), que por defecto da error: Android no sabe deshacer cambios.

    Después de onCreate() o de onUpgrade(), Android cambia el número del fichero por el de DB_VERSION: la próxima vez ya coinciden y no se hace nada. Sigue el camino con cada móvil:

    ¿Qué hace Android al abrir?cinco móviles, una misma aplicación con DB_VERSION = 3

    Todos estos móviles abren la aplicación nueva, que tiene DB_VERSION = 3. Elige uno y sigue el camino que toma Android.

      4.4onUpgrade(): una escalera de cambios

      onUpgrade() recibe dos números: oldVersion, el que tiene el fichero, y newVersion, el de tu código. Piensa en las versiones como una escalera: cada escalón es una versión de la tabla y cada subida, el cambio que lleva de una a la siguiente. Cada usuario empieza en el escalón de su versión y tiene que subir todos los que le quedan.

      En código, la escalera es un switch sobre oldVersion con un case por subida. El switch entra por el case de la versión que tiene el usuario y, como no lleva break, sigue ejecutando los case de debajo hasta el final. Cada cambio usa ALTER TABLE … ADD COLUMN, que ya conoces de Bases de datos: añade la columna sin tocar las filas que había.

      Sube la escaleracada usuario empieza en su versión

      Elige un usuario y pulsa Abrir la aplicación nueva. Fíjate en qué case entra, por cuáles pasa y qué les ocurre a sus ciudades. Después marca la casilla del break y repite con Ana.

        Cada cambio, en dos sitios
        onCreate() crea la última versión, para los usuarios nuevos. onUpgrade() lleva a la última versión a quienes ya tienen la aplicación. Si cambias la tabla y olvidas uno de los dos, la aplicación falla solo a una parte de los usuarios.
        
      
        Comprueba · Verdadero o falso
        Si cambias el CREATE TABLE y no subes DB_VERSION, quienes ya tienen la aplicación se quedan con la tabla antigua.
        ALTER TABLE … ADD COLUMN borra las filas que ya había en la tabla.
        Quien instala la aplicación por primera vez pasa por todos los case de onUpgrade().
        Con un break en cada case, quien viene de la versión 1 se queda sin la columna surface.
        Si no subes la versión, Android ve que coincide y no llama a onUpgrade(). ADD COLUMN conserva las filas, con NULL en la columna nueva. Quien instala por primera vez no tiene fichero: pasa por onCreate(), no por onUpgrade(). Con break, el switch sale después del primer case que ejecuta.
        
      
        Comprueba · Elige
        La aplicación tiene DB_VERSION = 3. Un usuario que tenía instalada la versión 2 actualiza la aplicación. ¿Qué se ejecuta?
        La base de datos ya existe, así que onCreate() no se ejecuta. Como su versión, 2, es menor que 3, Android llama a onUpgrade() con oldVersion = 2: el switch entra por el case 2, porque la columna del case 1 ya la tenía.

        Insertar y consultar
        

      
        5.1Insertar con ContentValues
        
      
        Para insertar una fila podrías escribir el INSERT en SQL, pegando los valores a un String. Es fácil equivocarse con las comillas y, si el valor lo escribe el usuario, peligroso. Android da una forma más segura: un ContentValues, que guarda los datos de la fila como pares columna-valor.
        
      
      
        Es parecido a las preferencias de la rama 3.1: cada valor va con un nombre, que aquí es el de su columna.

          Comprueba · Verdadero o falso
          insert() devuelve -1 si no ha podido insertar la fila.
          Con ContentValues hay que escribir el INSERT en SQL.
          Si a query() se le pasa null como condición, devuelve todas las filas.
          Al cerrar la aplicación se vacía la tabla.
          insert() devuelve el número de la fila nueva, o -1 si falla. Con ContentValues no se escribe SQL: Android construye la sentencia. Sin condición, la consulta trae todas las filas. Los datos están en un fichero: siguen ahí al cerrar la aplicación.
          

    
          
    
          
      
          6
          Recorrer el resultado: el cursor
          

      
          query() no devuelve una lista, sino un cursor: un marcador que recorre las filas del resultado, una a una. Empieza antes de la primera fila, así que lo primero es moverlo.
          
      
      
          Como el dedo que sigue una lista
          Para leer la lista de clase en voz alta pones el dedo en la primera línea, lees los datos de esa línea y lo bajas a la siguiente. Cuando el dedo pasa de la última, has terminado. El cursor es ese dedo: solo se puede leer la fila sobre la que está.
          
      
          

          MétodoQué hace
          


          moveToFirst()Coloca el cursor en la primera fila. Devuelve false si no hay ninguna.
          

          moveToNext()Lo pasa a la fila siguiente. Devuelve false si ya estaba en la última.
          

          getString(i), getInt(i), getFloat(i)…Leen la columna i de la fila actual, contando desde 0 y en el orden en que se pidieron las columnas.
          

          close()Libera el cursor cuando ya no hace falta.
          
          

          
      
          
        
          Mueve el cursorrecorre el resultado de una consulta
          
        
          
          
          Es el resultado de pedir las tres columnas de todas las ciudades. El cursor empieza antes de la primera fila. Muévelo y lee las columnas de la fila en la que está.
          
          
          
          
          
            
          0 · cityName1 · poblation2 · surface
          
            
            
          
            
        
            
      
            
      
            Para recorrer todas las filas se combinan los dos movimientos en un do-while: si hay primera fila, se lee y se pasa a la siguiente mientras queden.
            
      
            El patrón para recorrer un cursor
            

            if(cursor.moveToFirst()){
    do{
        resultCities.add(cursor.getString(0));
    }while(cursor.moveToNext());
}
cursor.close();
            
      
            Comprueba · Ordena
            Ordena los pasos para leer todas las ciudades de la tabla.
            Leer la fila actual con cursor.getString(0)
            Cerrar el cursor con cursor.close()
            Pedir las filas con db.query(…)
            Repetir mientras cursor.moveToNext() devuelva true
            Comprobar que cursor.moveToFirst() devuelve true
            Primero la consulta, que da el cursor. Se coloca en la primera fila comprobando que existe, se lee y se avanza mientras queden filas. Al final, se cierra.

            TODO 7-8onUpgrade(): el switch sin break
            
      
            DBAccess.java
            

            @Override
public void onUpgrade(SQLiteDatabase sqLiteDatabase, int oldVersion, int newVersion) {
    switch(oldVersion){
        case 1:
            sqLiteDatabase.execSQL("ALTER TABLE " + DB_TABLE_NAME  +" ADD COLUMN " + POBLATION_COLUMN +" INTEGER");
        case 2:
            sqLiteDatabase.execSQL("ALTER TABLE " + DB_TABLE_NAME  +" ADD COLUMN " + SURFACE_COLUMN +" REAL");
    }
}
            
      
            Aquí la falta de break es a propósito
            Un switch sin break sigue ejecutando los case siguientes. Es justo lo que se necesita: el usuario empieza en la versión que tiene y aplica, en orden, todos los cambios que le faltan. Con un break, quien viene de la versión 1 se quedaría sin la columna surface.
            
      
            ALTER TABLE ... ADD COLUMN añade una columna sin tocar las filas que ya existen.

            Pruébalo
            

            1. Ejecuta la aplicación (Run) y pulsa Mostrar. La tabla está vacía, así que aparece el aviso de que no se ha podido recuperar.
            2. Pulsa Insertar con los campos vacíos. Aparece «Rellena los tres campos».
            3. Rellena los tres campos y pulsa Insertar. Después, Mostrar: aparece tu ciudad.
            4. Inserta otra ciudad y pulsa Mostrar. Sigue saliendo la primera, porque es lo que hace el método.
            5. Cierra la aplicación del todo y ábrela. Al pulsar Mostrar, los datos siguen ahí.
            6. Abre la base de datos con View → Tool Windows → App Inspection, pestaña Database Inspector. Ahí está la tabla con todas sus filas.
            7. Abre Logcat y filtra por tag:DB. Verás «Tablas creadas» solo la primera vez que se instala la aplicación.

            Errores comunes
            

            

            Lo que pasaPor qué
            


            no such column después de cambiar el CREATE TABLELa base de datos ya existía y onCreate() no se vuelve a ejecutar. Sube DB_VERSION y añade el cambio en onUpgrade(). Mientras desarrollas también puedes desinstalar la aplicación.
            

            Se cierra con SQLiteException al abrir, tras bajar DB_VERSIONLa versión no puede bajar: Android no sabe volver atrás. Vuelve a subirla o desinstala la aplicación.
            

            Quien viene de una versión antigua no tiene todas las columnasHay un break en el switch de onUpgrade().
            

            CursorIndexOutOfBoundsException al leerSe ha leído sin mover el cursor, o sin comprobar que moveToFirst() ha devuelto true.
            

            NumberFormatException al insertarSe ha convertido a número un texto vacío o no numérico.
            

            En el Database Inspector, 88.02 aparece como 88.0199966La superficie se trata como float, un tipo que guarda los decimales de forma aproximada. Con double la aproximación es mucho menor.
            

            Error de SQL al crear la tablaFaltan comas o espacios al concatenar el String. Míralo en Logcat, donde aparece la sentencia completa.
